interviewQuestions:
  - question: What makes a good REST API from the frontend's point of view?
    answer: |
      Predictable resource URLs and methods, correct status codes, one consistent error shape with
      machine-readable codes and field errors, pagination with a clear "next" pointer, filtering and
      sorting via query parameters, stable field names and types (ideally described by OpenAPI or
      shared schemas), and versioning or additive changes so clients do not break.
  - question: Offset or cursor pagination?
    answer: |
      Offset (`?page=3&limit=20`) is simple and allows jumping to page N, but becomes slow on large
      tables and shows duplicates or skips when items are inserted while paging. Cursor pagination
      (`?after=<opaque id>&limit=20`) is stable for live feeds and efficient with an index, but you
      cannot jump to an arbitrary page. Feeds and infinite scroll → cursor; admin tables → offset.
  - question: How do you make a POST safe to retry?
    answer: |
      Accept an `Idempotency-Key` header generated by the client; the server stores the key with the
      result of the first request and returns the same result for repeats instead of creating a
      duplicate (important for payments and orders on flaky networks). PUT and DELETE are idempotent
      by definition.
  - question: What is middleware and in which order should it run?
    answer: |
      Functions that run for every request (or a group of routes) before or after the handler.
      Typical order: request id and logging → security headers and CORS → body parsing and size limits
      → rate limiting → authentication → route-specific authorization and validation → handler → error
      handler. In Fastify the same is done with hooks (`onRequest`, `preHandler`) and a central
      `setErrorHandler`.

## Resources and methods

```text
GET    /orders?status=paid&sort=-createdAt&limit=20   list
POST   /orders                                        create   → 201 + Location
GET    /orders/123                                    read     → 200 / 404
PATCH  /orders/123                                    update   → 200 / 422 / 409
DELETE /orders/123                                    delete   → 204
POST   /orders/123/cancel                             action that does not map to CRUD
```

## A consistent error format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": { "fields": { "email": "Must be a valid email" } }
  }
}
```

RFC 9457 (`application/problem+json`) is a standard alternative.

## Cursor pagination

```http
GET /posts?limit=20&after=eyJpZCI6IjEwMjQifQ

{ "items": [...], "nextCursor": "eyJpZCI6IjEwMDQifQ" }
```

## Middleware / hooks pipeline (Fastify)

```ts
app.addHook('onRequest', async (request) => {
  request.log.info({ url: request.url }, 'incoming')
})

app.register(rateLimit, { max: 100, timeWindow: '1 minute' })

app.post('/orders', { preHandler: [requireAuth] }, async (request, reply) => {
  const input = CreateOrder.parse(request.body) // validation → 400 on failure via error handler
  const order = await orders.create(request.user.id, input)
  return reply.status(201).header('location', `/orders/${order.id}`).send(order)
})

app.setErrorHandler((error, request, reply) => {
  /* map known errors to status codes and the error format above */
})
```
